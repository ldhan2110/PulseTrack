Proposal

Today PulseTrack authenticates only through Keycloak (internal corporate identity, federated with the Blueprint directory). We need to invite external customers who have only an email — no Keycloak account — so they need email + password auth owned by PulseTrack.

Delivers

  • Dual login page (replaces the auto-redirect to Keycloak): "Sign in with company account" (Keycloak, unchanged) + email/password form (new).
  • PulseTrack-owned password auth for external users: password set via invite link, tokens issued by PulseTrack, silent refresh.
  • Isolation so external users cannot escalate into / masquerade as internal users, nor enumerate the internal directory.

Scope — OUT (deferred, do not build)

  • External self-registration (invite-only now; userType designed to allow it later).
  • Corporate email domain allowlist.
  • @InternalOnly route gating — external = normal platform user, same UI; data isolation stays per-project via ProjectMember.
  • Server-side refresh-token store / reuse-detection (tokens are stateless, rotated on use).
  • httpOnly cookie refresh (Option C+) — rejected, see Architecture.

Architecture

ASCII flow (archify not invoked — static fallback). Real component names match the tasks below.

FRONTEND (apps/web)
  LoginPage --"company account"--> keycloak.login()  (PKCE, unchanged) --> KC token (RS256)
           \--"email + password"--> POST /api/auth/login --> PT access (HS256) + refresh
  AuthProvider: no more hard redirect. Holds whichever token; silent-refresh timer.
    internal -> keycloak.updateToken()   external -> POST /api/auth/refresh (from localStorage)
  api.ts: Authorization: Bearer <access token>  (same header for both)

BACKEND (apps/api)
  Guard: AuthGuard(['jwt','external-jwt'])  -- passport tries both, first valid wins
    |- 'jwt'          RS256, Keycloak JWKS, issuer-locked      -> INTERNAL (unchanged)
    \- 'external-jwt' HS256, EXTERNAL_JWT_SECRET, iss=pulsetrack -> EXTERNAL (new)
  both resolve req.user = DB User -> all 42 existing controllers work unchanged

  AuthController (new): /auth/login  /auth/refresh  /auth/set-password  /auth/forgot-password
  AuthService: argon2 hash/verify, PT-JWT sign/verify, single-use token issue/redeem
  Admin invite (external) -> User{EXTERNAL,INVITED} + emailed single-use set-password link

Rejected: Option C+ (httpOnly cookie refresh) — rule conflict

rules.md: "No cookies/credentials (CORS origin:'*' relies on Bearer)." Browsers forbid Allow-Origin:'*' + credentials, and the product keeps wildcard CORS. So the refresh token lives in localStorage, not a cookie. Accepted tradeoff: XSS could read it → mitigated by short refresh TTL + rotate-on-use + CSP; server-side reuse-detection deferred.

Security invariants (enforced in code)

  • No cross-claim — Keycloak claim-by-email gated to userType=INTERNAL; an external row is never captured by a KC login (anti-squatting). security-critical
  • No Blueprint bleed — only the internal strategy runs Blueprint user-info sync.
  • No cross-validation — separate signing material + issuer; token-confusion rejected. security-critical
  • Directory scoping — user search scoped to shared membership (closes external→internal enumeration).

Backend contract

POST /api/auth/login           {email,password}            -> 200 {accessToken, refreshToken, user} | 401 generic
POST /api/auth/refresh         {refreshToken}              -> 200 {accessToken, refreshToken} | 401
POST /api/auth/set-password    {token, newPassword}        -> 200 (signed in) | 400/401 generic
POST /api/auth/forgot-password {email}                     -> 200 neutral (always)

All external-only. Only EXTERNAL + ACTIVE users log in. Rate limit on /auth/login. See spec.md req-1/5/7/8/9 for scenarios.
