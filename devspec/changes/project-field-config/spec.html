Configure task fields per project

Show/hide task-form fields per project via a settings dialog.

Context

id: project-field-config status: not yet on board depends_on: none

Adds Project.fieldConfig (independent of pending delete-project which adds Project.deletedAt — no conflict). Skills expected: backend, frontend, db, test, verify.

Proposal

Why. Every task form shows all fields; teams that don't use sprints, story points, or planned/actual dates see permanent noise. No per-project tailoring today.

Delivers. A per-project field-visibility config: an admin opens a "Configure Fields" dialog from Project Settings → General and toggles which task fields appear on the create and detail forms. Stored on the project, applied where those forms render.

In (v1)

  • Nullable Project.fieldConfig JSON map { fieldKey: boolean } (missing key = visible).
  • PATCH /projects/:projectId accepts fieldConfig; GET already returns it.
  • Dialog (shadcn Dialog + Switch) from a General-tab card, editable only by canManage.
  • 9 fields: Ticket type (required-by-default), Assignee, Priority, Sprint, Story points, Planned start, Planned end, Actual start, Actual end.
  • Hiding Ticket type allowed + warned; frontend drops its required check for hidden fields.
  • Hidden fields omitted from CreateTaskDialog + TaskDetailPage.

Out (v1)

  • Board/list columns + saved filters (still show all).
  • Bug forms, WBS task dialog (task only).
  • Custom fields; per-field defaults / fallback ticket type; backend enforcement.

Architecture (ASCII fallback — archify not invoked)

Project Settings (General tab)
  └─ [Configure Fields] (canManage) ─► ConfigureFieldsDialog
                                          │ local toggles ─► Save
                                          ▼
                       PATCH /projects/:projectId { fieldConfig }
                         RequirePermission(projectSettings, update)
                                          ▼
                       projects.service.update ─► Project.fieldConfig (JSONB)

Task forms read the same project object:
  useProject(projectId).fieldConfig
      ├─► CreateTaskDialog  ─ isFieldVisible(cfg,key) ? render (+required check) : skip
      └─► TaskDetailPage    ─ isFieldVisible(cfg,key) ? render : skip

Risk

Reversibility high (additive, UI-gated). Key risk: CreateTaskDialog currently hard-requires taskTypeId — must become conditional or hidden-config tasks can't be created. Low data risk (no existing-row writes, no destructive ops).

Backend

DB. ALTER TABLE "Project" ADD COLUMN "fieldConfig" JSONB; (mirrors workflowLayout Json?). Additive, nullable, no backfill.

DTO. UpdateProjectDto.fieldConfig? — @IsOptional() @IsObject().

Service. update() spreads fieldConfig when provided. findOne uses include → returns it, no read change.

Auth. Existing @RequirePermission('projectSettings','update') on PATCH :projectId. No new permission.

type FieldConfig = Partial<Record<FieldKey, boolean>>  // missing => visible
